# データベース設計

## 1. 目的

検査項目の標準名称と複数の別名を管理し、Pythonによる表記揺れの正規化・照合・英訳を支援する。

用語の追加・更新に対応し、変更履歴を追跡できる構成とする。

## 2. 使用技術（実装済み）

- データベース：SQLite
- バックエンド：Python / Flask
- データベース操作：SQLAlchemy

## 3. テーブル構成

`labtranslator/models.py` に定義した3テーブルを使用する。以下の型はSQLAlchemyの宣言に対応する。起動時にテーブルを作成し、SQLiteの外部キー制約を有効にする。DBは既定で `instance/labtranslator.db` に保存する。

### 3.1 lab_terms（検査項目マスター）

検査項目ごとの標準名称を管理する。

| カラム名 | 型 | 内容 |
|---|---|---|
| id | INTEGER | 主キー |
| japanese_name | VARCHAR(200) | 標準日本語名 |
| normalized_name | VARCHAR(200) | 標準名称の照合キー、一意 |
| english_name | VARCHAR(200) | 標準英語名 |
| specimen_type | VARCHAR | 検体の種類（必要に応じて設定） |
| seed_key | VARCHAR | 初期投入の固定識別子、一意・任意 |
| created_at | DATETIME | 登録日時 |
| updated_at | DATETIME | 更新日時 |

### 3.2 lab_term_aliases（別名マスター）

検査項目に対応する別名・略語を管理する。

| カラム名 | 型 | 内容 |
|---|---|---|
| id | INTEGER | 主キー |
| term_id | INTEGER | 検査項目マスターへの外部キー |
| alias_name | VARCHAR(200) | 別名・略語 |
| normalized_alias | VARCHAR(200) | Pythonで正規化した照合用文字列 |
| english_name | VARCHAR | 別名固有の英訳、空欄時は標準英語名 |
| specimen_type | VARCHAR | 別名に明記された検体情報 |
| seed_key | VARCHAR | 初期投入の固定識別子、一意・任意 |
| created_at | DATETIME | 登録日時 |

同じ検査項目に複数の別名を登録できる構成とする。

- `normalized_alias` は一意とし、標準名称との衝突も登録・更新時に検査する。
- 標準名称と異なる検体情報を含む別名は、その情報を別名固有の英訳に反映する。
- SQLiteの外部キー制約を有効にする。
- 初期マスターはデモ10項目と直接ビリルビン・間接ビリルビン・ナトリウムの13項目とする。`seed.py` の固定のseed_keyで再投入を判定し、既存レコードの編集を上書きしない。起動時と `init-db` コマンドで投入する。
- 登録・更新と変更履歴を同一トランザクションで保存する。
- 変更者は初期投入時seed、画面操作時local-userとする。認証は対象外とする。
- 通常入力のPDF原資料は `instance/<UUID>/source.pdf` に保存する。未修正の抽出文字列・修正値・照合結果・確認状態・抽出経路は同じフォルダーの `job.json` に保存する。3テーブルには用語マスター・別名とその変更履歴を保存し、報告書の行データは保存しない。

### 3.3 term_change_history（変更履歴）

用語マスターの登録・変更を記録する。

| カラム名 | 型 | 内容 |
|---|---|---|
| id | INTEGER | 主キー |
| target_table | VARCHAR | 変更対象のテーブル |
| target_id | INTEGER | 変更対象のレコードID |
| action | VARCHAR | create（登録）・update（更新）。削除機能は未実装 |
| before_data | TEXT | 変更前の内容（JSON形式） |
| after_data | TEXT | 変更後の内容（JSON形式） |
| changed_by | VARCHAR | 変更者 |
| changed_at | DATETIME | 変更日時 |

## 4. データの関連

- `lab_terms` と `lab_term_aliases` は1対多の関係とする。
- 別名は必ず対応する検査項目に関連付ける。
- 変更履歴は、対象のレコードと操作内容を記録する。
- 確認が必要なOCR結果は、別名として自動登録しない。利用者が用語マスター画面で登録する。
- 名称は1～200文字・制御文字なし、標準英語名は必須・200文字以内とする。括弧付き複合表記は構成要素ごとに登録し、別名の対応先が存在することを検査する。
- DB内の標準名称・別名の照合キーはそれぞれ一意とする。両テーブルをまたぐ重複・衝突は `save_term()` で検査する。
- `specimen_type` は検体情報を保持する欄であり、それだけで出力英訳を自動生成しない。別名固有の英訳を登録して反映する。

## 5. 照合の基本方針

1. 入力された検査項目名の原文を保持する。
2. Pythonで全角・半角、空白、括弧などを正規化する。
3. 正規化後の文字列を用語マスターと照合する。
4. 英語略語と日本語が混在する場合は、構成要素を確認して日本語部分を英訳する。
5. 照合キーが標準名称・別名に一致しなければ未登録とする。複合表記は各構成要素が同じ検査項目IDを指すことを確認し、不一致・未登録なら要確認とする。あいまい検索やOCR修正候補の自動提示は行わない。
6. 検査値・単位は変更しない。

## 6. 誤統一の防止

次の検査項目は、それぞれ独立した検査項目として管理する。

- 総ビリルビン：Total Bilirubin
- 直接ビリルビン：Direct Bilirubin
- 間接ビリルビン：Indirect Bilirubin

文字列の一部が一致するだけで、同じ検査項目と判断しない。

## 7. 報告書単位の英訳と保存範囲

- `master_translation`、`match_status`、`match_message` に用語マスター由来の候補と照合結果を保持する。
- `manual_translation`、`manual_english`、`translation_confirmed`、`translation_basis` 等に手動英訳と確認時の原文側データを保持する。いずれも報告書の `job.json` に保存し、DB構造は変更しない。
- 通常の再照合でも手動英訳を保持する。原文側の名称・値・単位・基準範囲の変更時は英訳確認を解除し、再確認を必要とする。
- 確認済みの手動英訳は比較画面・PDF・Excelに反映し、未確認の場合は出力英訳を空欄にする。元の用語照合状態と利用者の確認状態を区別する。
- 手動英訳の保存は用語マスター・別名を自動更新せず、term_change_historyにも記録しない。マスターの登録・更新とは独立した操作である。
- OCR連携と失敗記録は実装済みだが、実OCR精度は未検証である。OCR結果や修正候補を自動でマスターへ登録しない。

- 複数利用者間の用語登録の承認フロー（現在はローカル画面で入力検証して保存する）
- 利用者認証と変更者の識別
- マスターのExcel・CSV一括登録
- 用語の削除・無効化とその履歴記録
- 報告書の手動英訳の操作履歴、複数利用者の同時更新・競合検出
